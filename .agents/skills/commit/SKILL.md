# Commit

사용자의 커밋 요청을 실행 권한으로 받아, 요청 범위 안에서 변경사항 분석·분류·메시지 작성·커밋을 추가 승인 없이 완료한다. 사용자가 계획만 요청하거나 사전 확인을 명시한 경우에는 그 지시를 따른다.

## 1. 변경사항 분석

- 적용되는 AGENTS.md와 저장소의 커밋 규칙을 확인한다.
- `git status --short`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 확인한다. 추적되지 않은 파일도 내용을 확인해 포함 여부를 판단한다.
- 필요하면 `git log -5 --oneline`으로 최근 메시지 관례를 참고한다.
- Git 저장소가 아니면 위치 문제를 알리고 중단한다. 임의로 `git init`하지 않는다. 변경사항이 없으면 커밋하지 않고 알린다.

## 2. 논리적 단위 분류

- 하나의 목적을 이루는 코드, 관련 테스트, 문서는 함께 묶고 서로 독립적인 변경은 별도 커밋으로 나눈다.
- 사용자 요청 범위 밖 변경이나 기존 스테이징 항목을 임의로 포함하거나 해제하지 않는다. 범위는 요청과 대화 맥락으로 판단하며, "모든 변경사항" 요청이면 무시된 파일과 자격 증명을 제외한 전체 변경을 대상으로 한다. 판단할 수 없는 범위만 좁혀 질문하고, 이미 명확한 범위의 커밋에 승인을 요구하지 않는다.
- 같은 파일에 서로 다른 목적의 변경이 있으면 필요한 부분만 스테이징할 수 있도록 나눈다. 비밀 키와 자격 증명은 커밋 대상에서 제외한다.

## 3. 한국어 메시지 작성

메시지는 `type: 한국어 요약` 형식으로 작성한다. 타입은 다음 중 변경의 주된 목적에 맞게 고른다.

| 타입 | 용도 |
| --- | --- |
| feat | 새 기능 추가 |
| fix | 오류 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 문서 등 유지보수 |

예: `feat: 컴포넌트 생성 화면에 레트로 테마 적용`

커밋별 메시지와 포함 파일 또는 변경 구간을 정한다. 필요한 검증을 수행하고, 진행 안내가 유용하면 분류와 메시지를 짧게 알린 뒤 답변을 기다리지 않고 커밋한다. 미실행 검증이나 제외한 변경은 결과 보고에 명시한다.

## 4. 커밋 실행

- 커밋 직전 상태와 diff를 다시 확인한다. 변경이 있으면 내용을 재분석하고 요청 범위 안에서 분류와 메시지를 갱신해 계속 진행한다.
- 대상 파일은 `git add -- <경로>`로, 필요한 변경 구간은 부분 스테이징으로 추가한다. `git add .`로 무관한 변경까지 일괄 추가하지 않는다.
- `git diff --cached`로 실제 커밋 내용이 요청 범위와 분류에 일치하는지 확인하고 제안한 순서와 메시지로 커밋한다. 다른 변경이 이미 스테이징되어 있으면 그대로 섞어 커밋하지 말고 기존 상태를 보존할 방법을 정한다.
- 훅이나 Git 오류로 실패하면 원인을 확인한다. 훅을 우회하지 않는다. 요청 범위 안의 수정은 검증 후 계속 진행하고, 범위 밖 수정이 필요한 경우에만 사용자에게 필요한 결정을 묻는다. 동일 오류를 해결 없이 반복 실행하지 않는다.
- `git log -1 --oneline`과 `git status --short`로 결과를 확인하고 커밋 해시, 메시지, 남은 변경을 보고한다.
- 별도 요청 없이 push, amend, reset, 이력 재작성은 하지 않는다.
