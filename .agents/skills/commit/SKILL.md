# Commit

변경 의도를 파악해 검토 가능한 커밋 계획을 만들고, 사용자가 승인한 범위만 커밋한다.

## 1. 변경사항 분석

- 적용되는 AGENTS.md와 저장소의 커밋 규칙을 확인한다.
- `git status --short`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 확인한다. 추적되지 않은 파일도 내용을 확인해 포함 여부를 판단한다.
- 필요하면 `git log -5 --oneline`으로 최근 메시지 관례를 참고한다.
- Git 저장소가 아니면 위치 문제를 알리고 중단한다. 임의로 `git init`하지 않는다. 변경사항이 없으면 커밋하지 않고 알린다.

## 2. 논리적 단위 분류

- 하나의 목적을 이루는 코드, 관련 테스트, 문서는 함께 묶고 서로 독립적인 변경은 별도 커밋으로 나눈다.
- 사용자 요청 범위 밖 변경이나 기존 스테이징 항목을 임의로 포함하거나 해제하지 않는다. 포함 범위가 불명확하면 계획에서 명시한다.
- 같은 파일에 서로 다른 목적의 변경이 있으면 필요한 부분만 스테이징할 수 있도록 나눈다. 비밀 키와 자격 증명은 커밋 대상에서 제외한다.

## 3. 한국어 메시지와 계획 제안

메시지는 `type: 한국어 요약` 형식으로 작성한다. 타입은 다음 중 변경의 주된 목적에 맞게 고른다.

| 타입 | 용도 |
| --- | --- |
| feat | 새 기능 추가 |
| fix | 오류 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 문서 등 유지보수 |

예: `feat: 컴포넌트 생성 화면에 레트로 테마 적용`

각 커밋의 메시지, 포함 파일 또는 변경 구간, 주요 변경과 검증 결과를 제시한다. 미실행 검증이나 제외한 변경도 필요한 경우 알린다. 사용자에게 이 구체적인 계획의 승인을 요청하고 답변을 기다린다. 최초의 "커밋해줘" 요청만으로 제안한 계획이 승인되었다고 간주하지 않는다. 승인을 기다리는 이유가 이 스킬의 "사용자 승인 후 커밋" 절차임을 밝히고 이 SKILL.md를 링크한다.

## 4. 승인 후 커밋

- 승인 이후 상태와 diff를 다시 확인한다. 승인된 대상의 내용이 바뀌었거나 범위를 수정해야 하면 변경된 계획을 다시 승인받는다.
- 승인된 파일은 `git add -- <경로>`로, 필요한 변경 구간은 부분 스테이징으로 추가한다. `git add .`로 무관한 변경까지 일괄 추가하지 않는다.
- `git diff --cached`로 실제 커밋 내용이 승인 범위와 일치하는지 확인하고 제안한 순서와 메시지로 커밋한다. 다른 변경이 이미 스테이징되어 있으면 그대로 섞어 커밋하지 말고 기존 상태를 보존할 방법을 정한다.
- 훅이나 Git 오류로 실패하면 원인을 확인한다. 훅을 우회하지 않으며, 수정으로 승인된 내용이 달라지면 재승인을 받는다. 동일 오류를 해결 없이 반복 실행하지 않는다.
- `git log -1 --oneline`과 `git status --short`로 결과를 확인하고 커밋 해시, 메시지, 남은 변경을 보고한다.
- 별도 요청 없이 push, amend, reset, 이력 재작성은 하지 않는다.
